# Task 2 Report

## Part A · 집 Wi-Fi 주소

| 항목 | 값 |
|---|---|
| A1 인터페이스 주소 / 마스크 | `en0` 192.168.45.124, netmask 0xffffff00 = 255.255.255.0 (/24) |
| A2 서브넷 범위 (직접 계산) | 네트워크 192.168.45.0, 사용 가능 192.168.45.1 ~ 192.168.45.254, 브로드캐스트 192.168.45.255 |
| A2 Task 1 `network_range` 확인 | `('192.168.45.1', '192.168.45.254', '192.168.45.255')` - 일치 |
| A3 기본 게이트웨이 | 192.168.45.1 - 범위 안에 있음 |
| A4 바깥에서 본 공인 주소 | 222.239.45.105 |

- **A2 계산:** 마스크가 /24라 앞 24비트(192.168.45)가 네트워크, 뒤 8비트가 호스트다. 호스트 비트가 전부 0이면 네트워크 주소, 전부 1이면 브로드캐스트다.
- **A3:** 게이트웨이는 같은 서브넷 안에 있어야 한다. 서브넷 밖으로 나가는 패킷은 먼저 게이트웨이에게 링크 계층(ARP로 MAC 주소를 알아내서)으로 직접 전달해야 하는데, 직접 닿을 수 있는 건 같은 서브넷의 주소뿐이기 때문이다.
- **A5:** 192.168.45.124는 RFC 1918 사설 주소(192.168.0.0/16)이고 222.239.45.105는 공인 주소다. 그러니 NAT가 최소 1번 있다. traceroute를 보면 1번 홉이 공유기(192.168.45.1), 2번 홉이 바로 공인 주소 222.239.45.1이다. 이 주소는 내 공인 주소와 같은 /24라, 공유기의 바깥쪽 주소가 곧 내 공인 주소다. 따라서 **NAT는 공유기에서 1번**이다.
  - NAT가 2번이면, 공유기 다음 홉이 공인 주소가 아니라 사설 주소나 100.64.0.0/10(통신사 NAT 대역) 주소로 나오고, 공유기 관리 화면의 WAN 주소도 공인 주소와 다르게 나온다.
  - 4번 홉의 100.87.44.49도 100.64.0.0/10 대역이긴 하지만, 이미 공인 구간(2번 홉) 다음이므로 NAT가 아니라 통신사 내부 라우터의 주소다.

## Part B · 두 네트워크 비교

| | 집 Wi-Fi | 아이폰 핫스팟 |
|---|---|---|
| 맥의 IPv4 주소 | 192.168.45.124 | 192.0.0.2 |
| 마스크 | /24 | /32 (255.255.255.255) |
| 게이트웨이 | 192.168.45.1 | 192.0.0.1 |
| 공인 주소 | 222.239.45.105 | 211.234.180.156 |
| traceroute | 공유기 → 통신사 망 순서로 보임 | 8홉 모두 `*` (응답 없음) |

- **B3 공인 주소가 바뀐 이유:** 공인 주소는 내가 어느 통신사망을 통해 인터넷에 나가느냐로 정해진다. 집은 가정용 인터넷 회선, 핫스팟은 이동통신망의 주소를 받는다.
- **B3 사설 주소가 바뀐 이유:** 사설 주소는 접속한 네트워크가 정해 준다. 집은 공유기 DHCP가 192.168.45.0/24에서 하나를 줬다. 핫스팟은 통신사망이 IPv6 전용이라 상황이 다르다.
  - 맥이 IPv6 주소(2001:2d8:...)를 받았고, IPv4용으로는 특수 대역 192.0.0.2/32를 받았다.
  - ifconfig에 `clat46`과 `nat64 prefix 64:ff9b::/96`이 보인다. 즉 맥이 IPv4 패킷을 직접 IPv6로 바꾸고(CLAT), 통신사의 NAT64가 이를 다시 공인 IPv4 211.234.180.156으로 바꾼다.
  - 그래서 핫스팟의 게이트웨이 192.0.0.1은 /32 범위 밖에 있다. 진짜 옆 장비가 아니라 변환용 가상 게이트웨이이고, 인터페이스에도 `NOARP`가 붙어 있다.
- **핫스팟의 NAT:** 주소 변환은 2단계(맥의 IPv4→IPv6, 통신사 NAT64)다. 그중 여러 사용자가 공인 주소를 나눠 쓰는 NAT는 통신사 쪽 1개다. traceroute는 셀룰러망이 응답을 막아서 확인하지 못했다.

## Part C · DHCP (out/dhcp.pcapng)

| 번호 | 메시지 | IP 출발 → 도착 | 이더넷 목적지 |
|---|---|---|---|
| 8 | Discover | 0.0.0.0 → 255.255.255.255 | ff:ff:ff:ff:ff:ff (브로드캐스트) |
| 9 | Offer | 192.168.45.1 → 192.168.45.124 | f6:5c:df:15:2f:ef (내 MAC) |
| 10 | Request | 0.0.0.0 → 255.255.255.255 | ff:ff:ff:ff:ff:ff |
| 11 | ACK | 192.168.45.1 → 192.168.45.124 | f6:5c:df:15:2f:ef |

- 네 메시지 모두 같은 Transaction ID 0xbbe6fc0f를 쓴다.
- 앞의 1~6번은 맥이 예전 주소를 기억하고 Discover 없이 Request/ACK만 보낸 경우(INIT-REBOOT)다. 7번은 주소를 반납하는 Release다. 이전 기록을 지운 뒤에야 8~11번의 전체 DORA가 나왔다.
- **C2:** Discover의 출발지는 **0.0.0.0**, 목적지는 255.255.255.255다. 클라이언트는 아직 주소가 없어서 출발지를 "주소 없음"(0.0.0.0)으로 쓸 수밖에 없다. DHCP 서버가 어디 있는지도 모르니 목적지도 브로드캐스트일 수밖에 없다. 서버는 IP 주소 대신 Transaction ID와 내 MAC 주소(chaddr)로 누구에게 답할지 구분한다.
- **C3:** 서버가 준 임대 시간은 **21,600초(6시간)**다. 맥은 Discover에서 7,776,000초(90일)를 요청했지만 서버가 6시간으로 정했다. 절반인 3시간(T1)이 지나면 맥이 서버에 갱신 Request를 보낸다.
- **C4:** Discover는 브로드캐스트인데 Offer와 ACK는 192.168.45.124와 내 MAC으로 바로 갔다. 그 사이에 두 가지가 생겼기 때문이다.
  - 서버가 Discover에서 내 MAC 주소(chaddr)를 알게 됐다.
  - 서버가 줄 주소(yiaddr 192.168.45.124)를 정했다.
  - 맥은 broadcast flag를 0으로 보내 "주소가 아직 없어도 유니캐스트를 받을 수 있다"고 알렸으므로, 서버는 ARP 없이 그 MAC으로 직접 보낼 수 있다.
  - 반면 Request(10번)는 여전히 브로드캐스트다. 맥은 아직 0.0.0.0이고, 어느 서버의 Offer를 고를지(server id 192.168.45.1)를 다른 서버들에게도 알려야 하기 때문이다.
